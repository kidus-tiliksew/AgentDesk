# Mobile app

Lifecycle: evergreen component baseline. Delivery state: partly built. The shell is built: the configuration check, the provider stack, safe-area insets on the headerless screens, `(auth)/sign-in` with email-code sign-in and sign-up and recovery from an incomplete sign-up, account creation through `ensureAccount`, the route guards, the inbox header's history, rules, notifications, and settings links, and sign-out on `settings/account`. The inbox `(app)/index`, the agent screen `agent/[id]`, and the decision screen `decision/[id]` are built. Device registration, notification tap routing, foreground presentation, and device unregistration on sign-out are built. The connections screen `settings/connections` and the add-machine screen `settings/add-machine` are built, including a Mac's sign-in request and its connection (`req-mac-app` AC-2.2, AC-2.5). The history screen `history` and the decision screen's parent lookup for removed decisions are built. The rules list `settings/rules` and the rule editor `settings/rule/[id]`, which also serves `settings/rule/new`, are built. The notification settings screen `settings/notifications` and the first-launch time zone call are built. The digest screen `digest/[id]` and the digest push's tap route are built. The notification categories, their action buttons, and the answer from a button are built: the Android notification task, and on iOS the response listener with the local background-time module `modules/notification-action-background`. Account deletion on `settings/account`, with its notice on `(auth)/sign-in`, is built (§Notifications, **Account deletion**). Showing an answer relayed from an agent's chat (§Screens, **Answers given in chat**) is not built. The Settings tab `settings` and its rows are built. Anonymous usage analytics (§Analytics) are built. The Privacy Policy links (`req-mobile-app` REQ-7) are built. On Android, the `default` channel at high importance with private lock-screen visibility, edge-to-edge drawing, `expo-system-ui`, and the adaptive icon's monochrome layer (DEC-17) are built. The Maestro flows (§Verification) are not built. `submit.production.android` and `apps/mobile/store/play/` (§Stack) are not built. Every other screen is not built.

Implements: `req-mobile-app` REQ-1 to REQ-8; `req-accounts-and-connections` REQ-2, REQ-4, REQ-5, AC-6.2, AC-6.5, AC-6.6 (screens); `req-mac-app` AC-2.2, AC-2.5 (screens); `req-public-api-and-webhooks` REQ-3, REQ-4 (screens); `req-notification-rules` REQ-2 to REQ-4 (rules screens), REQ-5 (settings screens), AC-6.3 (digest screen); `req-decision-requests` AC-8.3 (screens)

This component owns the Expo app in `apps/mobile`: its screens, sign-in, live data, answering, notification categories and actions, device registration, and anonymous usage analytics (DEC-5, DEC-7). `component-website` owns the privacy policy text the app links to. Every rule and record it shows belongs to a backend component; the app enforces nothing the backend does not also enforce.

## Stack

Expo with Expo Router, built by EAS for iOS and Android. `ClerkProvider` from `@clerk/expo`, with its `expo-secure-store` token cache, wraps `ConvexProviderWithClerk`, so every query and mutation carries the person's Clerk session. Markdown renders with `react-native-markdown-display`. Validation messages come from `@agentdesk/contract`.

The root layout reads `EXPO_PUBLIC_CONVEX_URL` and `EXPO_PUBLIC_CLERK_PUBLISHABLE_KEY` before it mounts Clerk or builds the Convex client. When either is missing or blank, it shows a configuration screen that names the missing variables and never their values. `EXPO_PUBLIC_POSTHOG_KEY` and `EXPO_PUBLIC_POSTHOG_HOST` are optional, and `agentdesk:apps/mobile/src/config.ts#readConfig` returns `analytics: null` when the key is missing or blank (§Analytics). `apps/mobile/.env.example` holds placeholders only.

The app references Convex functions through each backend domain's `refs.ts` module, imported by relative path, for example `identity` from `../../../convex/identity/refs`. It never imports `convex/_generated/api`, so building and testing the app need no local `npx convex codegen`. A refs module imports function modules as types only, so the bundle carries no backend code.

The app's own `typescript` is the version Expo SDK 57 expects, 6.0; the other packages use the root version. Metro and Jest resolve workspace TypeScript sources such as `@agentdesk/contract`. Those sources import siblings with NodeNext `.js` specifiers, so `metro.config.js` and the Jest resolver retry a relative `.js` import from outside `node_modules` without the extension when it does not resolve.

`app.config.ts` sets the iOS bundle identifier and the Android package to `sh.kidus.agentdesk` and reads the EAS project id from `EAS_PROJECT_ID`. It sets the Android `googleServicesFile`, the Firebase configuration FCM needs, from `GOOGLE_SERVICES_JSON` when that variable is set, for example as an EAS file environment variable. It adds the `expo-notifications` config plugin, which adds the iOS push entitlement and names `default` as the Android default notification channel. `ios.entitlements` declares `com.apple.developer.usernotifications.time-sensitive: true`, so every prebuild and EAS build carries the entitlement iOS requires to present a push whose `interruptionLevel` is `time-sensitive`, which the backend sets on urgent decision pushes (`component-notifications` §Push sound). The Apple App ID must have the Time Sensitive Notifications capability before a build can sign with the entitlement; EAS capability sync normally enables it at the next build. A build or signing failure caused by a missing capability is reported to the operator, and the entitlement stays. `android.adaptiveIcon` draws `assets/adaptive-icon.png`, the white Prompt bubble mark, over `#4f46e5`, with `assets/adaptive-icon-monochrome.png` as `monochromeImage`, the layer Android 13 and later tint for themed icons (DEC-17(5)). `expo-system-ui`, at the version Expo SDK 57 expects, applies `userInterfaceStyle: "automatic"` on Android, so the app follows the system light or dark setting there as on iOS. The app takes the minimum, target, and compile Android API levels Expo SDK 57 ships, 24, 36, and 36, and `app.config.ts` overrides none of them (DEC-17(1)). The generated `gradle.properties` sets `edgeToEdgeEnabled=true`, so every Android screen draws edge to edge (DEC-17(2)). It adds the `@clerk/expo` config plugin with `appleSignIn: false`. The plugin sets the iOS deployment target to 17.0, the minimum for Clerk's native module, in both `ios/Podfile.properties.json` and the Xcode project's `IPHONEOS_DEPLOYMENT_TARGET`, so every prebuild and EAS build gets it. With `appleSignIn: false`, it adds no Sign in with Apple entitlement, because the app signs in by email code only. `apps/mobile/ios` and `apps/mobile/android` are generated, git-ignored output that the app never edits. `eas.json` defines `development`, a development client for physical iOS and Android devices, `development-simulator`, which extends it for the iOS simulator, and `production`, a store build in the EAS `production` environment that increments the iOS build number and the Android version code from the remote app version; it sets no Android `buildType`, so EAS builds an Android App Bundle (DEC-18(2)). `submit.production.ios.ascAppId` names the App Store Connect app. `submit.production.android` submits to the Play `internal` track with the Google service account key EAS stores, so the repository holds no key (DEC-18(3)). `apps/mobile/store/screenshots/` holds the App Store screenshots and `apps/mobile/store/play/` holds the Play listing text, the Data safety answers, and the Android phone screenshots (DEC-18(6)). Linking the EAS project, adding the APNs key, the FCM HTTP v1 key, and the Play service account key to EAS, supplying `google-services.json`, and running and submitting builds are operator acts; `component-repository` §Mobile releases owns the release procedure.

The package entry is `apps/mobile/index.ts`. It imports `src/notification-action-task.ts` before `expo-router/entry`, so the notification action wiring runs at module scope when the app starts in the background, before any screen mounts (§Notifications). `expo-task-manager` is at the version Expo SDK 57 expects, `~57.0.21`. Its config plugin only adds the iOS `fetch` background mode, which the app does not use, so `app.config.ts` does not list it. Prebuild still applies it, as one of Expo's automatic plugins for installed packages, so the generated iOS `Info.plist` declares `fetch`. No `remote-notification` background mode is configured, because receiving a push in the background is not how a button press reaches the app. The local Expo module `apps/mobile/modules/notification-action-background` holds Swift source, the podspec `NotificationActionBackground`, which depends on `ExpoModulesCore` and `ExpoNotifications`, and an Apple-only `expo-module.config.json` naming `NotificationActionBackgroundModule` and the app delegate subscriber `NotificationActionBackgroundAppDelegateSubscriber`. Expo autolinking finds it under `modules/`, and prebuild adds its pod to the generated iOS project. Android neither links nor loads it.

A native iOS build needs Node 22 and Xcode 27 or later. Xcode 26.1.1 (Swift 6.2.1) cannot compile `expo-modules-jsi` 57.1.1 or `clerk-ios` 1.6.1. Expo Go cannot load the app, which depends on `expo-dev-client` and Clerk's native module, so local runs use a development build (`npx expo run:ios` or `npx expo run:android`). A native Android build needs Node 22, JDK 17 or later, and the Android SDK at `ANDROID_HOME`. The Clerk instance must not require a password, because the app collects only an email address and a code. The instance must have the Convex integration active, which adds `aud: "convex"` so `ConvexProviderWithClerk` sends the session token itself. Its session token must also carry the custom claim `"email": "{{user.primary_email_address}}"`, which `ensureAccount` requires. The Convex deployment needs `CLERK_JWT_ISSUER_DOMAIN` and its pushed functions before the first sign-in. `apps/mobile/README.md` walks through these first-run steps for both platforms with placeholders only.

## Analytics

`AnalyticsProvider` in `agentdesk:apps/mobile/src/analytics.tsx#AnalyticsProvider` wraps everything below the root layout's configuration check, so screen views cover sign-in too. With `analytics: null` it renders its children and mounts no PostHog client, so the app sends nothing (`req-mobile-app` AC-8.3). Otherwise it mounts `PostHogProvider` from `posthog-react-native` with the configured key and host, and these settings:

| Setting | Value | Effect |
| --- | --- | --- |
| `personProfiles` | `"never"` | no person profile; the app never calls `identify` (AC-8.1) |
| `disableGeoip` | `true` | PostHog derives no location from the request IP address (AC-8.1) |
| `autocapture` | `captureScreens: false`, `captureTouches: false` | no touch events, whose element text would carry decision content (AC-8.2) |
| `captureAppLifecycleEvents` | `true` | Application Installed, Updated, Opened, and Backgrounded |
| `enableSessionReplay` | `false` | no session recording (AC-8.2) |
| `disableSurveys`, `preloadFeatureFlags` | `true`, `false` | no survey or feature flag requests |

`ScreenViews` calls `posthog.screen` on each route change with `screenName(useSegments())`, which drops layout groups and keeps dynamic segments as patterns, for example `/agent/[id]`, so no id leaves the device (AC-8.1). The app sends no other event. `posthog-react-native` brings in `expo-application`, `expo-file-system`, and `expo-localization`, so adding or changing it needs a new native build.

The Settings tab's About section and the sign-in screen hold the two Privacy Policy controls (`req-mobile-app` REQ-7). `PRIVACY_POLICY_URL` in `src/config.ts` is `https://agentdesk.kidus.sh/privacy`. Each control has the link role and the accessible name "Privacy Policy", and a press calls `WebBrowser.openBrowserAsync(PRIVACY_POLICY_URL)` from `expo-web-browser`, which shows the page in an in-app browser sheet.

Screens drawn without a navigation header add the device's safe-area insets to their 24-point padding through `src/headerless-screen.tsx`, so their content clears the status bar, the camera cutout, and the home indicator. They are sign-in, the configuration screen, both group layouts' loading states, and the account gate's own states. Expo Router's root supplies the safe-area context. Screens under a stack header keep their padding without the insets, since the header already clears the status bar. On Android the system Back gesture or button pops the current stack and, on a tab root, leaves the app, as React Navigation does by default; the app installs no `BackHandler` override (DEC-17(3)).

The `(auth)` layout sends a signed-in person to `(app)`, and the `(app)` layout sends a signed-out person to `(auth)/sign-in`. Inside `(app)`, the account gate calls `identity/accounts:ensureAccount` once for each Clerk session after Convex accepts the session's token, and mounts the routes only after it succeeds. The first sign-in therefore creates the account before any screen issues a Convex call (AC-2.1). A result for an earlier session is dropped. A transient failure offers a retry. An `unauthenticated` refusal ends the Clerk session. The `(app)` stack registers route files without layout edits, and each screen sets its own title.

Every list reads a Convex reactive query, so creations, settlements, cancellations, and status changes appear without user action while the app is open (`req-mobile-app` AC-2.3). Agent cards show display name, topic, state, status line, time since update, pending count, and a stale marker (AC-2.2). An agent card's bold title is the session's display name, at most two lines, so the title stays fixed while status updates arrive, as the agent screen's title does. The second line is the status line in secondary text, at most two lines; a session without a status line shows its state label there, or "No status yet" before any status. The meta line is the topic, the state label, and the time since update, joined by " · ", then the amber "Stale" marker when the session is stale. It always shows the state label and does not repeat the display name. The pending count is a pill on the right, drawn only above zero, before the chevron. The card's accessibility label is "Agent: " with the display name. Its description lists the state, the full status line, the topic, the stale marker, the pending count including zero, and the update time, so the two-line limits never shorten what a screen reader reads. An answer rejected as `conflict` shows the stored outcome instead of the attempt (AC-3.2).

The inbox reads `decisions/app:listPending` and `agents/app:liveAgents` and keeps each query's order, so decisions stay urgent first, then by deadline, then oldest (AC-2.1). Filtering removes items and never reorders them. A section shows loading until its query returns and an empty state when it returns nothing. A failed query shows a failure with a retry, never an empty list. The agent screen reads `agents/app:get`. It shows `not_found`, and `invalid` naming `agentSessionId`, as the not-found state; any other failure offers a retry. Both screens catch query errors in a boundary keyed by the screen's input. Decision rows open `decision/[id]` and agent cards open `agent/[id]`. Both routes sit under `(app)`, so a direct link keeps the sign-in guard and the account gate.

The topic chips are "All topics" followed by every distinct topic of the unfiltered decisions and live agents and each of its slash-delimited parent prefixes, deduplicated and sorted. For `acme/billing/invoices` the chips include `acme`, `acme/billing`, and `acme/billing/invoices`. One chip is selected at a time. A selected chip filters both sections with `topicMatches` from `@agentdesk/contract`, the rule notification rules use, so `acme` keeps `acme/billing` and drops `acmecorp` (AC-2.4). When a selected topic leaves both lists, the selection returns to All topics.

`settings/connections` reads `identity/connections:listConnections` and keeps its order, newest first connection first. Each row shows the client name, the machine name or "Machine unknown", "First connected" with its time, and "Last used" with its time or "Never used" (`req-accounts-and-connections` AC-4.1). A signed-in Mac is a connection like a harness: the query returns its API token with the name "AgentDesk for Mac", the Mac's machine name, `firstConnectedAt`, and an optional `lastUsedAt` (`component-identity` §Short-code sign-in). The screen renders it with the same row, machine grouping, times, spoken description, and revocation as a harness, and needs no client field to do so (`req-mac-app` AC-2.5). A Mac with no `lastUsedAt` shows the same never-used state. `src/connections/format.ts` shows the times in the device's locale and time zone to the minute, because the backend writes `lastUsedAt` at most once a minute. The screen shows loading until the query returns, "No machines connected" with "Run the AgentDesk installer on a computer, or open AgentDesk for Mac, then enter the code it shows." and an Add machine button for an empty list, and a failure with a retry, never an empty list, when the query fails. Each row's Revoke action is labelled with the name and machine. It opens the system's destructive confirmation, an action sheet on iOS and an alert on Android (DEC-9, DEC-17), titled "Revoke <name> on <machine>?", or "Revoke <name>?" when the machine is unknown, with the message "Its next request will fail." The list's footer reads "Swipe left or touch and hold to revoke. A revoked connection fails its next request." Both statements cover a harness and a Mac. Cancel closes the confirmation without a call. Confirming calls `identity/connections:revokeConnection` with the row's `credentialId` (AC-4.2). The open confirmation owns the mutation hook, so the list binds no mutation until a revocation is being confirmed. While the call runs, the screen sends no second call and disables every row's controls. A failure keeps the row and the confirmation and shows "Could not revoke <name>. Try again." The screen never removes a row itself; the reactive query drops a revoked connection. An "Add machine" link above the list opens `settings/add-machine`. The link sits outside the screen's query-error boundary, so it stays available while the list loads, when it is empty, and when its query fails. The installer tells the person to choose Add machine.

`history` reads `decisions/app:searchHistory` through `decisions.app.searchHistory` in `convex/decisions/refs.ts` with Convex's `usePaginatedQuery` (`component-decisions` §History). Its stack title is "History". The inbox header links to it before Connections and Account. The route sits under `(app)`, so a direct link keeps the sign-in guard and the account gate.

- **Search.** The field is labelled "Search history". Its trimmed text is sent as `query` 300 ms after the last change. A newer edit and leaving the screen cancel the pending timer, so typing issues no query per keystroke. Blank text sends no `query`. The backend matches the text against titles, bodies, answers, and notes (AC-6.1), and the app filters nothing itself.
- **State.** The state chips are All states, Answered, Expired, and Cancelled. A chip other than All states is sent as `state`. Pending is not offered.
- **Topic.** History has no loaded topic list that covers every page, so its topic chips do not come from the loaded rows. The person types a topic in the field labelled "Topic" and presses Apply topic. The app normalizes the topic with the contract's `normalizeTopic`. An invalid topic shows the topic rule and sends no query. The chips are All topics, then the applied topic and each of its slash-delimited parent prefixes from `topicChips`, drawn by `TopicFilter`. Applying selects the applied topic. The selected chip is sent as `topic`, and the backend matches it by `topicMatches`, so `acme` keeps `acme/billing` and drops `acmecorp`. The chips stay until another topic is applied, so an empty result or a cleared filter never removes them. State and topic changes apply at once.
- **Pages.** The list sits in a `QueryErrorBoundary` keyed by the sent `query`, `state`, and `topic`. Convex binds each cursor to its query, so every input change discards the loaded pages and starts again from the first page. The first page and each Load more request 20 rows; the server clamps a request to 1..50. Rows keep the query's order, and a row that a live change shows on two loaded pages appears once, at its first position. Load more requests the last page's continuation cursor once. While that page loads, the button reads "Loading more" and is disabled. The button disappears when the query reports the end. An empty page that is not the end shows Load more, not an empty state.
- **States.** The screen shows "Loading history" until the first page returns. When the query reports the end with no rows, the screen shows "No settled decisions." without search text or a filter and "No matches." with either. A failed page shows "Could not load your history." with Try again, never an empty list. The search and filter controls sit outside the boundary and stay usable while the list loads or fails.
- **Rows.** Each row shows the title, topic, state, "Settled" with `settled_at` in the device's locale, and an answer summary. The summary is "Answer: " with the answer through `formatAnswer`, "Default applied: " with the applied default, "Expired without an answer", or "No answer was recorded." for a cancelled decision. For a decision answered in chat, the summary is "Answered in chat: " with the answer, and the row shows the user's chat message below it, cut to two lines. Pressing the row opens `decision/[id]`.
- **Delete.** Each row has a Delete action labelled with the decision title. It replaces a swipe gesture, so the app adds no gesture dependency and the action is reachable by screen readers. It opens a confirmation in the row that names the decision and states that deletion removes it from every screen. Cancel closes the confirmation without a call. Confirming calls `decisions/app:remove` with the row's decision id (AC-6.2). The open confirmation owns the mutation hook, so the list binds no mutation until a deletion is being confirmed.
- **One deletion at a time.** The deletion state lives above the list's boundary, and a ref set before the call refuses a second call until the first settles. While a call runs, every row's Delete, the confirmation's controls, and the search and filter controls are disabled, so no input change remounts the list during the call. A call that settles after the screen unmounts changes nothing.
- **Delete results.** A success closes the confirmation. A failure keeps the row and the confirmation and shows 'Could not delete "<title>". Try again.' The retry sends the same id. `conflict` shows "This decision is pending and cannot be deleted." `not_found` shows "This decision was removed elsewhere." Both close the confirmation. The screen never removes a row itself and never leaves History; the reactive query drops a removed decision.

A follow-up keeps its removed parent's id as `parent_id` (`component-decisions` §Removal). The decision screen reads the parent through `decisions/app:get` in its own error boundary keyed by the parent id (`src/decision-parent.tsx`). It shows "Loading parent" until the query returns, then the Parent decision link. `not_found`, and `invalid` naming `decisionId`, show "Parent decision unavailable" without a link. Any other failure shows "Could not load the parent decision." with Retry parent. The follow-up's details and answer controls stay usable in every case. Opening a removed decision shows the decision screen's not-found state.

**Answers given in chat.** The user can answer a decision in the asking agent's chat, and an agent relays that answer through `resolve`. The decision then reads as answered with `answered_via` `chat` and carries the user's chat message word for word (`req-decision-requests` REQ-8, DEC-13; `component-decisions` records it, `component-contract` defines the read shape). The app shows it as given in chat wherever it shows a settled decision's answer and how it was settled (AC-8.3):

- **Decision screen.** The settled outcome names the answer as it does for any answer, and its line saying how and when the decision was settled reads "Answered in chat" with the time. Below the outcome, a card labelled "Your message in chat" shows the chat message in full as plain text, never rendered as Markdown, so it reads exactly as the user typed it. The outcome's accessibility label includes "Answered in chat", and the card's label reads the message.
- **History, digest, and notification outcomes.** History rows, digest decision rows, and the outcome notification of a button press each say "Answered in chat" (§Screens, **Rows**; §Screens, **Decisions**; §Notifications, *Outcomes*).

The app never records a chat answer: it sends no `chat` surface and offers no way to relay one. It reads no `interactive` flag and shows no marker for an interactive decision, which is an ordinary pending decision in the inbox, on the agent screen, and on the decision screen. Its push may never be sent, because push for an interactive decision waits for a hold and is sent only if the decision is still pending (`req-notification-rules` REQ-8). When the decision is answered in chat, the reactive queries drop it from the inbox and the agent screen's pending list and add it to History, and an open decision screen switches to the settled outcome. An answer sent afterwards from the decision screen, an inbox card, or a notification button gets `conflict`, and the app shows the chat answer as the stored outcome (`req-mobile-app` AC-3.2).

`settings/rules` reads `notifications/rules:list` through `notifications.rules` in `convex/notifications/refs.ts`, and `agents/app:liveAgents` and `agents/app:recentAgents` through `agents.app` (`component-notifications` §Rules; `component-agent-presence` §Reads). Its stack title is "Rules". The inbox header links to it after History and before Connections and Account. Both rules routes sit under `(app)`, so a direct link keeps the sign-in guard and the account gate. The labels and agent names come from `src/rules/format.ts`.

- **List.** Rows keep the query's order, latest save first. Each row shows the action (Push, Digest, or Mute) and four lines: "Topic", "Agent", "Event", and "Priority", each with its value or "Any" when the rule leaves it unset. Event kinds read "Decision created", "Decision expired", "Agent stale", "Agent status changed", and "Agent done". The agent is the card name of a live agent, the name with "(ended)" for a recent agent, and "Ended agent" for a session that neither query returns, the name the backend's push messages use. The row's accessibility label is "Rule: " followed by all five values. Pressing a row opens `settings/rule/[id]`. The list binds no mutation hook.
- **List states.** All three queries sit in one `QueryErrorBoundary`. The screen shows "Loading rules" until every query returns. `settings/notifications` reads `notifications/settings:getSettings` and saves with `notifications/settings:updateSettings`, both through `notifications.settings` in `convex/notifications/refs.ts` (`component-notifications` §Settings). Picking the zone already stored still sends it, so an explicit UTC is recorded. A success replaces the draft with the returned settings and shows "Settings saved." A child component that mounts with the loaded form owns the `updateSettings` hook, so the loading and failure states bind no mutation, and the hook is called only on a press.
- **Refusals and failures.** An `invalid` refusal naming `timeZone`, `quietStart`, `quietEnd`, `digestTime`, or `staleThresholdMinutes` shows under that field. An `invalid` refusal naming any other field, or none, shows "AgentDesk refused these settings. Check the fields and save again." Any other failure shows "Could not save your settings. Check your connection and try again.", keeps every edit, and turns Save into Retry, which sends the same arguments again. An edit after a failure returns the button to Save, which checks the draft again. A failure never shows success.
- **One call at a time.** A ref set before the call refuses another until the first settles. While it runs, Save reads "Saving..." and every field and choice is disabled.
- **Live changes.** A changed query result replaces the draft only while the draft is unedited, no save runs, and no failure is shown, so a live change never erases an edit. A save that settles after the screen unmounts, or after its Clerk session ended, changes nothing.

`digest/[id]` reads `notifications/digests:get` with `{ digestId }` through `notifications.digests` in `convex/notifications/refs.ts` (`component-notifications` §Digest read). A digest push opens it (§Notifications). Its stack title is "Digest". An event that names a decision without a title shows "Decision unavailable", and one whose session is gone shows "Ended agent". - **Times.** `sent_at` and `occurred_at` show in the device's locale and time zone through `toLocaleString`, not in the account's digest time zone.

The query sits in a `QueryErrorBoundary` keyed by the digest id, so a new id starts clean. `settings/add-machine` is the approval side of short-code sign-in (`req-accounts-and-connections` REQ-6). Its stack title is "Add machine". Lookup returns `found` with `machineName` and harness ids, or `not_found`, `expired`, or `locked`. A Mac's request returns `found` with `machineName`, an empty harness list, and `client: "macos"` (`component-identity` §Short-code sign-in). - **Code entry.** The field is labelled "Installer code", with the placeholder "ABCD-EFGH" and the guidance "Enter the 8-character code shown by the installer." The app trims surrounding whitespace, uppercases letters, and drops one hyphen between the fourth and fifth characters. Find machine is enabled only for exactly eight ASCII letters or digits after that. Longer input and other separators are refused, never truncated or stripped. The backend checks the code alphabet, the request, its owner, and the lock. Every mutation sends the normalized code.
- **Lookup.** Lookup records a wrong-code attempt on the backend, so only a press of "Find machine" sends it, never typing, mounting, or a timer. While it runs, the button reads "Finding machine...". A found request shows "Machine" with the machine name, "Harnesses" with each display name, and "Approve to connect these harnesses on this machine." A Mac's found request shows the machine name with "wants to connect", one "AgentDesk for Mac" row in place of the harnesses, and "Approve to connect AgentDesk for Mac on this machine." in place of the harness note. Its row is one accessibility element labelled "AgentDesk for Mac on <machine>", so VoiceOver and TalkBack name the app and the requesting machine (DEC-9(2), DEC-17(4)). The screen connects nothing until Approve (AC-6.2; `req-mac-app` AC-2.2). The code field is disabled while a request is shown. "Use another code" clears the request and the field and returns to entry without a call.
- **Approve and decline.** A child component that mounts with the found request owns the approve and decline hooks, so code entry binds neither. Both send the code captured with the found request, never a later field edit. Approve reads "Approving..." while it runs. A returned `approved` shows "The machine is connecting. The installer will finish on its own." Decline reads "Declining..." while it runs. A returned `declined` shows "Request declined. Run the installer again for a new code." (AC-6.6). Both outcomes remove Approve and Decline. A Mac's request uses the same controls, calls, and outcome messages. "Enter another code" clears the outcome and the field without a call.

Check the code and try again." `expired` shows "That code expired. Run the installer again for a new code." Both return to editable entry, and editing the code clears the message. `locked` shows "Too many wrong codes. Try again in 10 minutes." and disables the field, Find machine, and every retry (AC-6.5).

A timer ends the window, and a return to the foreground reads the clock again, because a suspended app runs no timers. When the window ends, entry returns with its guidance and no call is sent. The backend still checks the lock on every later call. The timer and the listener end when the screen unmounts.

Check your connection and try again." A failed decline shows "Could not decline the request. Check your connection and try again." Approval and decline failures keep the found request. A response that does not match the typed shapes shows the same failure and is logged with `console.warn`.

An agent card's time since update counts from `status_at`. A session with no status yet shows "No status yet" and "No update yet" rather than its activity time. ## Notifications

The notification code is `src/install-id.ts`, `src/notification-route.ts`, and `src/notifications.tsx`; the first-launch time zone call reads the device zone through `deviceTimeZone` in `src/notification-settings.ts`. The notification action code is `src/notification-actions.ts`, `src/notification-action-auth.ts`, `src/notification-action-background.ts`, and `src/notification-action-task.ts`, with the native module in `modules/notification-action-background`. It uses `expo-notifications`, `expo-device`, and `expo-task-manager` at the versions Expo SDK 57 expects.

**Install id.** The install's `deviceId` is a UUID from `expo-crypto`, stored in `expo-secure-store` under `agentdesk.installId`. The app stores the id before it first uses it and never deletes it, so the id survives restarts, sign-outs, and another account's sign-in. Concurrent first uses share one creation and store one id. A storage failure fails the setup, and the app never registers an id it has not stored.

**Registration.** After the account gate mounts the routes, the app starts registration for the Clerk session. On Android it first creates the `default` channel, named "Decisions and agents", with high importance and `lockscreenVisibility` `AndroidNotificationVisibility.PRIVATE` (`agentdesk:apps/mobile/src/notifications.tsx#DeviceRegistration`). It reads the notification permission and asks once per session when the system allows another prompt. A denied permission registers nothing. The app reads the EAS project id from `Constants.expoConfig.extra.eas.projectId`. It waits for this launch's notification action categories to settle, which never fails, and then gets the Expo push token for that project. It then calls `notifications/devices:registerDevice` with the install id, the token, `ios` or `android`, and the device name. The name falls back to the model name and then to the platform. A native push-token change gets a new Expo token and calls `registerDevice` again. The raw APNs or FCM token never reaches the backend. A return to the foreground runs the setup again without a prompt, so a permission granted in system settings or a failed setup recovers. An unchanged token sends no second call.

Setup never blocks a screen. A missing EAS project id, a runtime without push such as a simulator, a storage failure, a token failure, and a registration failure each leave the screens working. Each shows a message with a retry on `settings/account`. A denied permission shows there that notifications are off and points to system settings. Missing push configuration does not extend the root configuration check.

**Session binding.** Each start is a run tied to one Clerk session. A run ends when the session changes, when the account gate unmounts the routes, or when sign-out starts, and its listeners are removed when it ends. A token, permission, or registration result from an ended run is dropped. All device mutations run on one queue, so an unregistration waits for a registration already sent.

**Sign-out.** `settings/account` first stops registration for the session and waits for any registration already sent. It then calls `notifications/devices:unregisterDevice` with the stored install id and ends that exact Clerk session (AC-4.2). An install with no stored id was never registered and skips the call. When the unregistration fails or the id cannot be read, the session stays signed in. The screen shows "Could not stop notifications on this device. Check your connection and try again." and the button allows another attempt. When Clerk's sign-out fails after the unregistration, the screen shows "Could not sign out. Try again." Once sign-out starts, registration stays stopped for the session, so a later token change cannot register the device again. The install id stays stored.

**Account deletion.** `settings/account` shows a destructive Delete Account row below Sign out (`req-accounts-and-connections` REQ-5, AC-5.1). It asks in the system's own destructive confirmation, as Sign out does: an action sheet on iOS and an alert on Android, titled "Delete your AgentDesk account?". The message says that deletion is permanent, that every connected machine and device is disconnected now, and that decisions, agents, rules, and notification settings are removed within 24 hours. Cancel calls nothing. A typed confirmation is not used; the system confirmation with its separate cancel choice guards the action (Apple HIG Action sheets). `AccountDeletionProvider` in `src/account-deletion.tsx` runs the deletion. It is mounted at the root inside `NotificationProvider`, so it outlives the (app) routes, which the account gate can unmount before the sign-out finishes, for example during a Convex reconnect. One deletion runs at a time, for the Clerk session captured at confirmation:

1. It stops registration for the session and waits for any registration already sent, as sign-out does.
2. It checks that the captured session is still the active Clerk session, takes a fresh token with the same `getToken` call `ConvexProviderWithClerk` makes, checks again that the captured session is active, and checks that the token's `sid` claim names the captured session. It calls `identity/accountDeletion:deleteAccount` through a `ConvexHttpClient` made for this call and authenticated with that token only, never through the shared Convex client, whose authentication follows whichever session is active and which resends an unacknowledged mutation after reconnecting. A queued deletion therefore never runs, and is never replayed, under another session. When another session became active first, nothing is sent and that session's screens show no deletion; when the token names another session while the captured one is still active, the screen shows the deletion failure. The backend revokes every connection and removes every device of the account, this install included, so the app sends no `unregisterDevice`, which the backend would refuse. The install id stays stored.
3. It ends that exact Clerk session. A completion for a session that is no longer current therefore never signs out another session.

`(auth)/sign-in` then shows "Your account is being deleted. Its data will be removed by <completeBy>." on the email step, with `completeBy` from the mutation's result in the device's locale. The notice belongs to the deleted session; another session signing in clears it. While the deletion runs, the row reads "Deleting Account..." and both rows are disabled. When the mutation fails, the session stays signed in and the screen shows "Could not delete your account. Check your connection and try again.", announced to screen readers, with a Try Again row that repeats the deletion. Once the backend has committed the deletion, the account can do nothing more, so the provider draws its own screen above every route for the captured session until the sign-out succeeds, whether or not the account gate still shows the routes. That screen is titled "Deleting your account", states "Your data is removed by <completeBy>.", and shows "Signing out" while the sign-out runs. When the sign-out fails, it shows "Your account is being deleted, but this device could not sign out. Try again.", announced to screen readers, with a Try Again button that retries only the sign-out, never another deletion or `unregisterDevice`.

**First-launch time zone.** Once the account gate has mounted the routes, the app reads the device's IANA zone through `Intl.DateTimeFormat().resolvedOptions().timeZone` and calls `notifications/settings:initializeTimeZone` with it (`component-notifications` §Settings). It sends at most one call per Clerk session in each app launch. The root `NotificationProvider` holds the set of sessions already sent and marks a session before the call, so strict mode's repeated effects and a remount of the routes, such as a Convex reconnect, send nothing more. A new session in the same launch sends again, and a new launch starts with an empty set, so a failed call is retried on the next launch. A zone that the runtime does not report, a zone `Intl.DateTimeFormat` refuses, and an error while reading it send nothing, which keeps the backend's UTC fallback. The call goes through the existing Convex client from `useConvex`, not a mutation hook, so no route binds an extra hook on its first render. Its result changes nothing on screen. A failure is caught and dropped, so it never blocks a screen and leaves no unhandled rejection. The backend sets the zone only while nobody has chosen one, so the app never replaces a zone the person chose in settings, including an explicit UTC.

**Foreground presentation.** A push that arrives while the app is open shows in the banner and the notification list with no sound and no badge change. On Android, a notification without sound shows in the list without a heads-up banner. Receiving a push never navigates and schedules no local notification. The inbox's reactive queries update on their own (AC-2.3).

**Tap to open.** The root layout captures notification taps above the route guards. It reads the live response listener and the response that launched the app, which it clears after capture. Only a body tap, the default action, routes; an action button press belongs to §Notification actions and opens no screen. A tap waits until the account gate has mounted the routes, then opens one screen (REQ-4). `decision.created` and `decision.expired` with a `decisionId` open `decision/[id]`, and `agent.stale`, `agent.status_changed`, and `agent.done` with an `agentSessionId` open `agent/[id]`. A digest push, whose data is `{ kind: "digest", digestId }` with no `eventId` (`component-notifications` §Digests), opens `digest/[id]` with its `digestId`. The id must be 1 to 128 letters, digits, `_`, or `-`. Missing, malformed, or unknown data opens the inbox. The app builds typed routes and never follows a path or URL from the payload. The opened screen's query checks existence and ownership. A response seen before is ignored, so a launch tap that the live listener also delivers opens one screen. A tap still waiting when its Clerk session ends is dropped, so it cannot open in the next session.

**Notification actions.** At startup the app registers three categories whose action buttons answer without opening the app (AC-4.1):

| Category | Actions (id: title) |
| --- | --- |
| `decision-approve-reject` | `approve`: Approve, `reject`: Reject |
| `decision-choice-2` | `option-1`: Option 1, `option-2`: Option 2 |
| `decision-choice-3` | `option-1`: Option 1, `option-2`: Option 2, `option-3`: Option 3 |

Action titles are fixed when a category is registered, so a choice notification names its options in numbered order in the body, and the buttons name the numbers. Every action sets `opensAppToForeground: false` and `isAuthenticationRequired: true`, so a locked iPhone asks for Face ID or the passcode before any action runs, Approve and Reject alike. Android has no unlock requirement for a notification action and ignores the flag. The `default` channel's private lock-screen visibility hands the choice to the device's lock-screen setting instead: a locked phone set to hide sensitive content shows only the app name, with no text or buttons, until it is unlocked, and a phone set to show all content shows the buttons on the lock screen, where a press answers without unlock (DEC-17(6)).

*Startup.* `index.ts` imports `src/notification-action-task.ts` before `expo-router/entry`. At module scope it installs a response listener, reads the launch response without clearing it, so the root layout still reads a body tap that launched the app, and starts one shared initialization per process. That initialization registers each category once through `setNotificationCategoryAsync`, which replaces the same definition on every launch. On Android it also defines the notification task `agentdesk-notification-action` at module scope with `TaskManager.defineTask` and registers it through `Notifications.registerTaskAsync` unless `TaskManager.isTaskRegisteredAsync` reports it registered. iOS registers no notification task. A failed category or task registration logs a warning and leaves the app and device registration working. Device registration waits for this initialization to settle before it requests the Expo push token.

*How a press reaches the app.* On Android, expo-notifications runs the notification task for a button pressed while the app is in the background or not running. On iOS the notification task never receives a button press, because expo-notifications 57 runs it only when a push is received, so the response listener and the launch response carry the press. On both platforms a press while the app runs also reaches the response listener. Every path calls one handler. It accepts only a response whose action id belongs to its registered category, whose data has kind `decision.created`, and whose `decisionId` is 1 to 128 letters, digits, `_`, or `-`. It reads Android's `dataString` push body when `data` is empty. A push receipt, a body tap, an unknown action, an action of another category, and malformed data do no authentication work, send nothing, and post nothing. A bounded registry keyed by the notification request id and the action id gives each press one owner in the process. A repeated delivery, such as the launch response that the listener also delivers, or the Android task and the listener for one press, waits on the owner and sends nothing. The backend's settlement protects a press seen again after a restart or on another device; the app does not claim exactly-once delivery.

*iOS background time.* expo-notifications calls the system completion handler for a response before JavaScript runs, so iOS may suspend the app before the answer is sent. The local module `modules/notification-action-background` closes that gap. Its app delegate subscriber registers a delegate through expo-notifications' public `NotificationCenterManager.shared.addDelegate` in `application(_:didFinishLaunchingWithOptions:)`, early enough for a response that launches the app in the background. It does not replace the `UNUserNotificationCenter` delegate. For each of the seven category and action pairs, the delegate begins a `UIApplication` background task inside `didReceive`, before expo-notifications completes the response, and returns `false`, so expo-notifications still hands the response to its emitter and the launch response. Default taps, other actions, and other notifications get no background task. A bounded native registry keyed by request id and action id holds one window per press, and a repeated delivery shares it. The native module `NotificationActionBackground` exposes `begin(requestId, actionId, categoryId)`, `finish(id)`, and the event `onExpire`. `begin` adopts the delegate's window, or begins one when the delegate saw none, and returns `{ id, state }` with state `running`, `finished`, `expired`, or `unavailable`. Each task ends once, when JavaScript finishes it or when iOS expires it, and an ended window stays readable, so a late `begin` cannot revive it. JavaScript ends the window only after the mutation and the dismissal or outcome notification have settled, including a failed dismissal or a failed local notification. iOS grants about 30 seconds and guarantees no duration and no execution after a cold start. When the window expires before the mutation is sent, no mutation starts and the app posts the generic failure once while JavaScript still runs; if iOS suspends the app first, the press can end with no notification. A mutation already sent is not rolled back or retried, and only a valid result counts as a success. A window iOS refused to grant, a build without the module, and a window an earlier JavaScript context finished protect nothing; the press is still answered, without protected background time. Android never loads the module.

*Authentication.* The handler gets the person's session outside React from the Clerk singleton that `ClerkProvider` also uses. When the provider already made it, `getClerkInstance()` returns it unchanged, so its token cache stays the provider's. Otherwise `getClerkInstance({ publishableKey, tokenCache })` makes it with the provider's publishable key and the same `@clerk/expo/token-cache` object, which restores the stored client token. When Clerk is not loaded, the handler loads it with the provider's native options, `standardBrowser: false` and `runtimeEnvironment: "headless"`, and concurrent presses share one load. It requires an active session and captures its id. It takes a fresh token with `session.getToken({ skipCache: true })`, which the Clerk Convex integration issues with `aud: "convex"`, and checks that the active session id is unchanged after every await and again immediately before the mutation. It sends the decision id and the action id (`approve`, `reject`, `option-1` to `option-3`) to `decisions/app:answerFromNotification` through a `ConvexHttpClient` made for that press and authenticated with the token. The backend maps the action to the answer and records `answeredVia: "notification"` (`component-decisions` §App functions). The app sends no answer, surface, user id, or agent credential, and never parses option ids from the notification body. Sign-out already unregisters the device and ends the Clerk session, so a press on a notification delivered before sign-out finds no session. The app keeps no other sign-out state for actions.

*Outcomes.* A result that parses as the contract's answered `Decision` dismisses the source notification with `dismissNotificationAsync` and posts nothing. A failed dismissal logs a warning and sends nothing more. Every other result posts one immediate local notification titled AgentDesk, with no category, with `{ kind: "decision.created", decisionId }` as its data, and on Android in the `default` channel:

| Situation | Body |
| --- | --- |
| `conflict`, answered in chat | `Answered in chat: <recorded answer>` |
| `conflict`, answered any other way | `Already answered: <recorded answer>` |
| `conflict`, expired with its default applied | `Expired: decided by default: <recorded answer>` |
| `conflict`, expired without an answer | `Expired without an answer` |
| `conflict`, cancelled | `Cancelled without an answer` |
| No active session, a session that ended or changed before sending, no token, a token refusal with status 401 or 404, or `unauthenticated` | `Sign in to AgentDesk to answer` |
| Any other failure, including a Clerk load or network failure, a `conflict` without a readable stored decision, a malformed result, and a window that expired before sending | `Could not answer. Open AgentDesk to try again.` |

The recorded answer is formatted from the stored decision as the decision screen formats it: Approve, Reject, or the stored option label, never the button that was pressed. A local notification that cannot be scheduled logs a warning, and the app never reports a success for a failed call. A tap on an outcome notification routes as a decision tap. It has no buttons, so it cannot re-enter the action path. Foreground presentation is unchanged.
